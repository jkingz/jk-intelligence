# API Guard (`lib/api/guard.ts`) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put one gate set and one response shape behind the 9 session-gated route handlers, so tenant isolation and the 401/403/503 decisions live in one file instead of eleven inline `new Response(...)` blocks.

**Architecture:** `lib/api/guard.ts` is a leaf: it calls `authAgent` for identity/role and `repository`'s two RLS-backed probes for tenancy, and returns either the value the route needs or a finished `Response`. Control flow stays in the route — the guard owns no ordering decision and implements no ownership rule. `lib/admin/http.ts` is deleted, not shimmed; its four helpers move to the guard.

**Tech Stack:** Next.js 16.3.5 fork (`RouteContext<T>`, awaited `ctx.params`, no `middleware.ts`), zod v4, Vitest 5 `unit` project with per-file `vi.mock` at module boundaries, Supabase `@supabase/ssr` session cookie, pnpm.

**Spec:** `docs/superpowers/specs/2026-10-10-api-hardening-design.md` → "Unit 2". Read it end to end first; the plan argues from it and does not restate its reasoning. Unit 1 is commit `e40d7bc` on this same branch — the single `NO_STORE` constant only exists because unit 1 collapsed the header set.

## Known deviations from the spec

Five, each found by reading the tests that have to survive. The task that enacts each one says so in one line.

1. **`gateSession()` answers 401 with `{ error: "Unauthorized" }`, not the caller's wording.** Today `app/api/metrics/{overview,keywords}` and `lib/exports/server.ts:70` answer 401 with `"Forbidden"` while admin/auth/boot answer `"Unauthorized"`. One status takes one sentence (King's call, 2026-10-11). No test asserts the old 401 body outside `me-route.test.ts:32`, so nothing fails — which is why each route task **adds** a body assertion rather than trusting a status-only one. The change is **wire-only**: the export menu (`components/features/data-export/components/export-menu.tsx:85-88`) branches on `response.status === 401` first and never reads `body?.error` for that status, so no user-visible string changes. (Corrected at Task 6 review 2026-10-12 — an earlier version of this line claimed the expired-session toast would start reading "Unauthorized"; it does not.)
2. **`gateAdmin(): Gate<null>`, not `Gate<AuthUser>`.** `requireAdmin()` returns `AccessDecision` with no user payload (`lib/agents/authAgent.ts:68-81`), and the three admin route tests mock `authAgent` with `requireAdmin` **only** (`clients-route.test.ts:17-19`). Deriving `AuthUser` inside `gateAdmin` would mean a second read the mocks cannot answer — a TypeError, not a 401. No admin route uses the identity today.
3. **A sixth export, `gateNullable<T>(read)`, carries the profile-shaped routes.** `/api/auth/me` and `/api/dashboard/boot` gate on `getProfileView()`, which lives under `components/features/user-profile/lib/`. Importing it from `lib/api/guard.ts` would make this the first `lib/ → components/` edge in the repo (grep: zero today) and would silently repoint `me-route.test.ts:5` / `boot-route.test.ts:21`'s mock boundary. So the route keeps its own `getProfileView` import and hands the function to `gateNullable`; the null→401 / throw→503 policy still lives in one file. `gateSession()` is `gateNullable(getAuthUser)`.
4. **`NO_STORE` is a header object, not a `Headers` instance.** Spec line 94 types it `Headers`. Both export routes build a `Response` with their own `Content-Type` + `Content-Disposition` and must spread it; a frozen `Headers` cannot be spread into a `ResponseInit`. It is `{ "Content-Type"... }`-free on purpose: `json()` adds `Content-Type` itself.
5. **`gateAdmin` adds the 503 the admin trio never had.** `context/architecture-context.md:88-91` documents their order and says nothing about a read failure, because `requireAdmin()` is awaited **outside** any `try` in all three handlers — a Supabase outage today produces an unhandled throw (500 HTML), against the standard in `code-standards`. `gateAdmin`'s `catch` turns it into the JSON 503 the standard asks for. Pinned by a new case in Task 5, not left as a silent improvement.

```ts
import "server-only";

import { type ZodError } from "zod";

import { getAuthUser, requireAdmin, type AuthUser } from "@/lib/agents/authAgent";
import { canAccessClient, listAccessibleClients } from "@/lib/db/repository";
import type { DashboardClient } from "@/types/dashboard";

/**
 * The cache pair every authenticated response carries, and nothing else. No
 * shared-cache freshness belongs here: a session-decided payload cannot be
 * CDN-cached, because Vary cannot name Cookie on Vercel (vary_key_denied:cookie).
 * Both export routes spread this into their own attachment response.
 */
export const NO_STORE = {
  "Cache-Control": "no-store",
  Vary: "Cookie",
} as const;

/** `extra` exists for the one header that is not a cache decision: `Retry-After`. */
export function json(body: unknown, status: number, extra?: Record<string, string>): Response {
  return new Response(JSON.stringify(body), {
    status,
    headers: { "Content-Type": "application/json", ...NO_STORE, ...extra },
  });
}

export function badRequest(message: string): Response {
  return json({ error: message }, 400);
}

export function unauthorized(): Response {
  return json({ error: "Unauthorized" }, 401);
}

export function forbidden(): Response {
  return json({ error: "Forbidden" }, 403);
}

export function databaseFailure(): Response {
  return json({ error: "Database operation failed" }, 503);
}

/**
 * A gate returns either the thing the route needs or a finished Response, so the
 * route keeps its own ordering and the denial shape lives in one place.
 */
export type Gate<T> =
  | { allow: true; value: T }
  | { allow: false; response: Response };

/**
 * One read, three outcomes: value → allow, null → 401, throw → 503. An identity
 * outage must never be reported as "you are logged out", which is why the catch
 * is per-gate rather than left to the handler.
 */
export async function gateNullable<T>(read: () => Promise<T | null>): Promise<Gate<T>> {
  try {
    const value = await read();
    if (value === null) return { allow: false, response: unauthorized() };
    return { allow: true, value };
  } catch {
    return { allow: false, response: databaseFailure() };
  }
}

export async function gateSession(): Promise<Gate<AuthUser>> {
  return gateNullable(getAuthUser);
}

/**
 * Role only, and `requireAdmin`'s reasons only — its decision carries no user, so
 * there is nothing to hand back. Deviation 2 in the plan.
 */
export async function gateAdmin(): Promise<Gate<null>> {
  try {
    const decision = await requireAdmin();
    if (decision.allow) return { allow: true, value: null };
    return {
      allow: false,
      response: decision.reason === "unauthenticated" ? unauthorized() : forbidden(),
    };
  } catch {
    return { allow: false, response: databaseFailure() };
  }
}

/** Ownership is Postgres' call. This forwards; it does not decide. */
export async function gateClientAccess(clientId: string): Promise<Gate<true>> {
  try {
    if (!(await canAccessClient(clientId))) {
      return { allow: false, response: forbidden() };
    }
    return { allow: true, value: true };
  } catch {
    return { allow: false, response: databaseFailure() };
  }
}

/**
 * The other tenant gate: routes that need the row, not just a yes. Same RLS path,
 * and the row it returns is the one the caller is allowed to see.
 */
export async function resolveAccessibleClient(clientId: string): Promise<Gate<DashboardClient>> {
  try {
    const client = (await listAccessibleClients()).find((entry) => entry.id === clientId) ?? null;
    if (!client) return { allow: false, response: forbidden() };
    return { allow: true, value: client };
  } catch {
    return { allow: false, response: databaseFailure() };
  }
}

/** Body, the zod issue's own message, or a shape error — in that order. */
export async function readJsonBody(
  request: Request,
): Promise<{ ok: true; value: unknown } | { ok: false; message: string }> {
  let raw: unknown;
  try {
    raw = await request.json();
  } catch {
    return { ok: false, message: "Send a JSON body." };
  }
  return { ok: true, value: raw };
}

export function firstIssueMessage(error: ZodError): string {
  return error.issues[0]?.message ?? "Check that value.";
}
```

```ts
import { z } from "zod";

import {
  badRequest,
  databaseFailure,
  gateSession,
  json,
  resolveAccessibleClient,
} from "@/lib/api/guard";
import {
  getCachedDashboardOverview,
  getCachedKeywordHistory,
} from "@/lib/db/repository";
import {
  DASHBOARD_RANGES,
  isDashboardRange,
  type DashboardRange,
} from "@/types/dashboard";

const clientIdSchema = z.uuid();

export async function GET(
  request: Request,
  ctx: RouteContext<"/api/metrics/[clientId]/overview">,
) {
  const { clientId: rawClientId } = await ctx.params;
  const clientId = clientIdSchema.safeParse(rawClientId);
  if (!clientId.success) return badRequest("Invalid client id");

  const rawDays = Number(
    new URL(request.url).searchParams.get("days") ?? DEFAULT_DAYS,
  );
  const days: DashboardRange = isDashboardRange(rawDays)
    ? rawDays
    : DEFAULT_DAYS;

  const session = await gateSession();
  if (!session.allow) return session.response;

  const access = await resolveAccessibleClient(clientId.data);
  if (!access.allow) return access.response;

  try {
    const [overview, history] = await Promise.all([
      getCachedDashboardOverview(access.value, days),
      getCachedKeywordHistory(access.value, days),
    ]);
    return json({ overview, history }, 200);
  } catch {
    return databaseFailure();
  }
}

const DEFAULT_DAYS: DashboardRange = DASHBOARD_RANGES[0];
```

`gateSession()` replaces the `if (!user)` block; `resolveAccessibleClient` replaces the `listAccessibleClients()` + `find` + 403. The route's `try` now covers only the two cached reads, which is what its 503 assertions (`overview-route.test.ts:122`) need; the gate covers identity and tenancy with the same 503 body.
